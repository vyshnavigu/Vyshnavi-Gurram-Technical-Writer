DocFlow AI: AI-Assisted Documentation Pipeline

by Vyshnavi Gurram, Technical Writer

I built DocFlow AI to explore how documentation can be generated from an API specification, checked when the specification changes, and prepared for review with the help of an AI model. I wanted to understand not only what could be automated, but also where the technical writer would still need to verify the content.

Overview

DocFlow AI is a proof-of-concept documentation workflow for FlowOps, a fictional automation platform. The sample API supports starting an automation job and checking its status. A separate Jira-style ticket proposes adding a job cancellation operation.

The project uses Python, Markdown, OpenAPI, GitHub Actions, and Groq with the openai/gpt-oss-120b model. I developed and tested the scripts using Google Colab.

Project scope

This is a personal project using fictional product requirements. It demonstrates a working process and the issues found during testing. It is not a production documentation platform.

Problem and Approach

When an API changes, its documentation may no longer match the implementation. A manual update can be missed, especially when changes are made across multiple files. I wanted the repository to identify outdated documentation rather than rely only on someone remembering to update it.

I also wanted to test whether an AI model could prepare an initial document from a proposed feature ticket. The model could save drafting effort, but its content had to be checked against approved sources. I kept the generated drafts separate from published API documentation and required human review.

Documentation Workflow

OpenAPI specification→Python generator→Markdown API reference→GitHub Actions validation

The Python generator reads spec/openapi.yaml and writes docs/generated-api.md. The GitHub Actions workflow checks the OpenAPI specification, regenerates the Markdown reference, and compares the output with the committed file.

Drafting from a proposed feature

FLOW-101 ticket+OpenAPI+Drafting rules→Groq model→Review draft

The drafting script reads a simulated Jira ticket, the OpenAPI specification, and the drafting rules. It sends these sources to the model and saves a Markdown draft marked as requiring human review. The ticket proposes POST /jobs/{jobId}/cancel, which is not present in the current OpenAPI specification.

This distinction matters. A requirement describes what the team wants to build. The API specification describes the operations currently documented. A draft should not describe a proposed operation as something customers can already use.

Documentation Drift Detection

Test scenario

I updated the description of POST /jobs in the OpenAPI file without updating the committed Markdown reference. I expected the validation workflow to fail because the documentation was outdated.

Unexpected result

The first validation run passed. After inspecting the repository in Colab, I found that generated-api.md had been committed at the repository root, while the generator wrote to docs/generated-api.md. The file in the docs folder was untracked, so the Git comparison did not identify its changes.

Correction and verification

I moved the committed Markdown file into the docs folder and reran the workflow. GitHub Actions then detected the changed description and failed at the drift check as expected. After updating the documentation to match the specification, the workflow passed.

GitHub Actions drift check
git diff --exit-code -- docs/generated-api.md
What I learned

A successful automated run does not necessarily mean a check is testing the correct file or condition. I needed to create a deliberate mismatch, inspect the output, and verify that the check failed for the expected reason.

Reviewing the AI-Generated Draft

For the AI test, I used FLOW-101, a proposed job cancellation feature. The model correctly identified the endpoint as proposed, but the first draft also introduced details that were not supported by the ticket or OpenAPI specification.

Example of an unsupported response

The ticket proposed HTTP 202 for an accepted cancellation request but did not define a JSON response body. The first draft included the following example:

Unverified response generated by the model
{
  "message": "Cancellation request accepted"
}

This response looked reasonable, but the source documents did not confirm the field or message. It was not suitable for approved API documentation.

The initial draft also added an authentication header and an empty JSON request body. I revised the drafting rules and generated another draft. Those examples were removed, but unsupported statements about cancellation behavior remained. In a later draft, the model generated an illustrative curl command for the proposed endpoint.

I stopped revising only the drafting instructions and introduced a Python quality checker. The test showed that more instructions did not always produce a more accurate document.

Quality Checks and Evaluation

The scripts/check_draft.py checker looks for selected problems we had already identified during human review. These include executable examples for an unverified endpoint, specified statements about unverified behavior, and punctuation that does not follow the project rules.

The checker initially detected three findings in the third draft. It missed the en dash characters because the original punctuation check looked only for em dashes. I updated the checker to recognise both, and the same draft then returned four findings with exit code 1.

Pull Request Review

I created a separate Git branch to add a documentation review checklist. The change was submitted through a GitHub pull request, where the automated checks passed. I reviewed the proposed file, recorded a self-review comment, and merged the pull request into main.

The checklist covers source verification, content quality, technical validation, AI draft review, and publication approval. This was a personal repository demonstration. It did not include an independent reviewer or enforced branch protection.

Results

By the end of the tested workflow, I had a Python-based API documentation generator, OpenAPI validation, a working drift check, an AI drafting script, automated checks for selected draft issues, and a GitHub Actions evaluation with positive and negative test fixtures.

The most useful outcome was understanding where automation needed another level of verification. A script can run successfully while checking the wrong file. An AI model can label a feature as proposed and still add details that are not in the source. Both situations require a way to inspect and test the output.

Limitations

The workflow uses a fixed sample ticket and a fictional API. The documentation generator supports the structures used in this example, rather than all possible OpenAPI definitions. The draft checker uses a limited set of patterns and cannot identify every unsupported technical statement.

The project does not automatically create pull requests for AI-generated changes, enforce independent approvals, or publish a full documentation site. Those are possible future improvements, but they are not part of the tested implementation described here.

The scripts, OpenAPI specification, test fixtures, and documentation are available in the DocFlow AI source repository.
